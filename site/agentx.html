先看结论

AgentX 是 SemiAnalysis 在 2026 年 8 月推出的推理基准场景。它把 393 条真实的 Claude Code 会话脱敏成"只有形状、没有内容"的记录,再原样重放给被测系统,看一套硬件加软件能以多快的速度、多低的成本服务这种流量。vLLM 两篇博客的全部标题数字都出自它。

1

它测的是服务效率,不是模型聪明程度

输出内容是合成的填充文本,输出长度被钉死在录制值上。智能体有没有把活干对,不在测量范围内;质量靠旁路的 GSM8K 测试把关。

2

默认的吞吐数字把缓存命中的输入也算进去

这批流量的输入输出比约 200:1,前缀缓存命中率在 95% 以上。"全部 token""未缓存输入加输出""仅输出"三种口径之间各差约一个数量级。引用任何 tokens/s 之前必须先问是哪一种。

3

"P90 交互速度"是慢的那一端

每个请求算一个样本(该请求内的平均 token 间隔),对它取第 90 百分位再取倒数。数字越大越好,但它描述的是较差的 10% 请求的边界。

4

成本和每兆瓦性能是套模型常量算出来的

每 GPU 小时的成本、每 GPU 的全口径功率都是 SemiAnalysis 模型里的固定值,不是现场实测。换一套价格假设,排名可能就变。

5

排名对阈值、基线引擎和日期都很敏感

同一组数据,Vera Rubin 对 GB300 的优势在不同交互速度阈值下是 2 倍、7 倍、63 倍或 2.7 倍。DeepSeek V4 Pro 上 AMD 和 NVIDIA 的性价比排名曾在一周内翻转。

6

配方由被测厂商的工程师编写和签核

NVIDIA 和 AMD 各有 5 名工程师是各自配置的代码负责人,硬件也由厂商和云商赞助。规则里有一套反特调条款,但没有成文的申诉程序,也没有找到独立第三方对结果的系统性复现。

一 · 它是什么

三块公开件,加一条两年的演进线

组成

  • 数据集。发布在 Hugging Face 上的 semianalysisai/cc-traces-weka-062126,以及为上下文窗口较短的模型准备的 -256k 变体。Apache 2.0,无需登录即可下载。
  • 负载生成器。agentx-harness,是 SemiAnalysis 对 NVIDIA 的 AIPerf 的分叉,可以 pip install。官方解释另维护分叉是为了更加厂商中立。当前版本 1.0.13(2026-11-03)。
  • 编排与打分代码。在 InferenceX 仓库里,负责起服务、跑重放、聚合指标、入库到看板。

沿革

时间事件与 AgentX 的关系
2025-10InferenceMAX v1三个固定形状场景(1k/1k、1k/8k、8k/1k),随机 token,有意避开前缀缓存。当时就承认这是缺口。
2026-02改名 InferenceX,发布 v2加入分离式推理和 Wide-EP,首次测 GB300 NVL72。文中自称数据只是"基线",真实性能至少这么好。
2026-03 至 071k/8k、1k/1k 相继弃用理由是把集群时间让给智能体编程基准。数据集的预览版迭代了至少 5 版。
2026-08-24InferenceX v3 + AgentX 1.0正式发布,首发 5 个模型。
2026-08 至 11harness 1.0.1 至 1.0.13都是小修,官方声明不影响可比性。大改留给尚未发布的 1.1。

为什么固定形状的基准不够

固定形状基准的每个请求都是一条提示、一次预填充、一段固定续写,然后丢弃。智能体流量有四个它抓不住的性质:

  • 多回合。一个会话几十到几百次交互,后一步依赖前一步的结果。
  • 长上下文、短输出。每次请求都带着完整的、不断增长的历史。
  • 高前缀复用。第 n 回合的输入等于第 n-1 回合的输入加输出,能否留住缓存决定了成本。
  • 子智能体突发扇出。主智能体一次派出多个子任务,造成尖峰式的缓存分配与淘汰。

官方仍认为固定形状的数据有用:它剥掉会话层行为,反映底层芯片和内核的性能,是读 AgentX 结果的基线。8k/1k 场景目前仍在维护。

二 · 数据集

393 条会话是怎么来的

采集

  • SemiAnalysis 自建了一个代理,架在 Claude Code 和 Anthropic API 之间,逐条记录请求。母语料有 8,271 个会话、341 万次请求、约 6,133 亿 token。常被引用的"300 万美元"是这批母语料按列表价估算的 token 花费。
  • 公开的 393 条是其中的子集,全部是 Claude Code 会话,采集期在 2026 年 4 月中到 6 月 21 日之间。贡献者是 SemiAnalysis 的内部员工。
  • 为了拿到子智能体的归属关系,SemiAnalysis 称与 Anthropic 合作,在 Claude Code 里加了两个请求头。

入选条件

  • 每会话至少 20 次请求,没有上限。
  • Claude Code 版本不低于 2.1.139(子智能体请求头上线的版本)。
  • 同时在跑的子智能体组峰值不超过 10 个。
  • 剔除含图片的会话,剔除标题生成、安全监控这类小调用,剔除完全重复的行。
  • 单次请求输入超过约 99 万 token 的行被当作计数伪影删掉。
  • 通过筛选的全部会话都入选,不是随机抽样。子集与母语料分布的对照没有公布。

三 · 脱敏与合成

删掉全部内容,只留下能决定缓存行为的结构

  • 公开数据里没有任何文本。没有提示词、没有回复、没有工具名和参数。每条请求只剩时间戳、模型名、输入输出 token 数、原始耗时、子智能体归属,以及一串缓存块标识。
  • 每 64 个 token 切一块,每块连同其前缀算一个哈希。发布前再把哈希映射成会话内的小整数。于是"第 k+1 轮的块列表以第 k 轮的列表开头,再追加几块"这个结构被原样保留,这正是前缀缓存能命中的部分。
  • 哈希只在单个会话内有效。不同会话之间的整数互不相干,这顺带切断了跨会话关联的可能。
  • 重放前用被测模型自己的分词器把内容"重建"出来。每个块标识确定性地映射到一段恰好 64 个 token 的填充文本,同一标识在任何请求里解码出的内容逐字节相同。
  • 历史里的助手消息也是合成的。它按录制的输出长度生成,不是被测服务器实际生成的文本。这样每一轮的块结构才能在不同服务器之间保持一致。

这样做的代价

  • 看不到服务商一侧的东西。对话模板、专有分词器、服务端工具、加密的思考内容、图片和文档的 token 展开,都只能用占位符和按模型校准的填充来近似。重建的 token 数与服务商实际计数之比,中位数是 1.004。
  • 只校准了 token 数,没有校准行为。工具调用的节奏、输出长度、何时派子智能体,都是 Claude 加 Claude Code 的行为。被测的开源模型在同样任务下会走出不同的轨迹,这一点无从体现。
  • 没有工具调用和系统提示的边界。当前格式是扁平的块序列,所以评估不了"把低复用的工具流量导到专用预填充实例"这类感知负载结构的技术。官方把保留这些边界列入了下一版数据集的计划。

四 · 重放

闭环重放:并发数是"同时活着的会话树"

会话结构

  • 每条记录变成一个根会话,主智能体的请求按顺序成为各轮。每轮发送的是完整的、不断增长的消息数组,和普通聊天客户端一样。
  • 子智能体被挂成依赖图:在父会话的前一轮上分叉出去,在后一轮上汇合。父会话要等这些子会话全部结束才发下一轮。时间上重叠的子智能体并发发出,各自按录制的相对偏移启动。
  • 有些并行智能体在原始记录里被摊平成与主智能体交错的请求。harness 用块标识的最长公共前缀把它们识别出来,拆成独立的子会话。
  • 工具执行时间没有单独字段,它包含在回合间隔里。重放按"上一请求结束到下一请求开始"计时,所以不会把原服务器的响应时间重复计入。

并发和闭环

  • 并发数 N 的含义是同时存活 N 棵会话树(一个根会话加它的全部子智能体),不是 N 个在途请求。子智能体不占名额,所以扇出时在途请求数可以高于 N。
  • 闭环:每一轮只在上一轮完成、再等够录制的间隔之后才发出。服务器慢,整条会话就整体后移,负载不会堆积。不提供请求速率的旋钮。
  • 一棵树跑完后,名额立即回收给下一条记录。并发数超过 393 时,同一条记录会同时出现在多个名额上。
  • 每次播放都在首条用户消息前插入一个唯一标记。这样并发副本或回收副本之间不会虚假共享缓存,同时保留会话内的共享。副作用是所有会话共用的系统提示也无法跨会话命中。

两条空闲上限回答了一个实际问题:很多会话是跨天挂着的(时长 P90 为 47 小时),怎么塞进一小时?答案是活跃段按原节奏放,长时间停顿被压到最多 300 秒。

输出长度被钉死

  • 每次请求的 max_tokens 等于录制的输出 token 数,并强制 ignore_eos=true。被测模型本来会生成多长、何时想停,都不起作用。
  • 被测模型实际生成的文本不会回灌进后续轮次。
  • 录制的模型名被改写成被测模型。原本"Opus 当主、Haiku 当子"的模型混用,只在树形结构里留下痕迹,所有请求都打到同一个模型。

每个并发点都要重启服务器

一次部署只测一个并发。扫一条曲线通常要 6 到 8 个并发点,每点重启服务器、重新预热、测满一小时。所以一条曲线的墙钟成本是十几个机时起步。

两处文档不一致:覆盖率校验的阈值,源码是 95%,教程一处写 98%。另外 harness 里还保留着一个早期预设(1,800 秒、起点 0% 至 100%),官方说两个预设的结果不可直接等同。自己复现时要说清用的是哪一个。

五 · 指标

每个数字是怎么算出来的

所有延迟和吞吐指标都在客户端测得,由 AIPerf 的逐请求记录聚合而来。服务端的监控数据只用于缓存命中、KV 占用这类辅助量。

指标算法读的时候注意
首字时延 TTFT请求发出到第一个内容 token 到达,跨请求取百分位看板默认用 P90
token 间延迟 ITL(请求总时长 − TTFT)÷(输出 token 数 − 1)是一个请求内的平均间隔,不是逐个间隔的分布。思考 token 计入输出
TPOT代码里和 ITL 是同一组数只是换了名字
P90 交互速度1 ÷ P90(ITL)先对延迟取 P90 再取倒数,所以是慢尾。每个请求一个样本
端到端延迟请求发出到最后一个 token官方自己说它在 AgentX 里意义变小,因为主要被最长的 10% 输出拖着走
端到端归一化交互速度1 ÷ P90(端到端延迟 ÷ 输出 token 数)近似 1 ÷(TPOT + TTFT ÷ 输出长度),把首字等待摊进去。输出越短受罚越重
每芯片吞吐窗口内 token 总数 ÷ 窗口时长 ÷ 芯片数分输入、输出、总计三种,见下文

吞吐里算哪些 token:最容易读错的一处

  • 默认口径是"总计":输入加输出。输入用的是每个请求的完整输入长度,不区分是否命中缓存。被缓存复用的前缀,每一轮都会再计一次。
  • 看板另有"仅输入""仅输出"两条独立的纵轴,以及一个"未缓存输入加输出"的开关(界面上叫 Horace He metric,目前没有对普通访客开放)。
  • 三种口径各差约一个数量级。按看板文档对线上数据的统计,智能体行的输入输出比中位数是 133:1,GPU 前缀缓存命中率中位数是 0.92。据此推算,总计口径约是仅输出的 134 倍,未缓存加输出口径约是仅输出的 12 倍。
  • 分离式部署还有一个陷阱:总吞吐按全部芯片归一,但"仅输入""仅输出"两条轴按预填充池、解码池各自的芯片数归一。所以在这两条轴上,分离式配置看起来每芯片更快,历史数据的中位数差约 2 倍。

横轴的定义在变

1.0 发布文章用的是常规交互速度,并要求与 TTFT 一起看。后来的 Rubin 文章改用"整响应 ITL"口径。仓库现行规则把端到端归一化交互速度定为主前沿,其他横轴视图上只显示同时也在主前沿上的点;但看板代码里它仍标为实验性模式。看板还会自己重算交互速度字段,因为 harness 的定义曾经漂移过。不同时期的点,口径可能不完全相同。

缓存指标

  • 理论命中率由数据集本身决定,是"无限缓存"下的上限。实测命中率从各引擎的监控接口读取。
  • 看板把每个并发点的输入 token 拆成三段:芯片显存内命中、主机内存层命中、重新计算。
  • KV 卸载在吞吐上没有单独加分。它让更多前缀被复用,收益直接体现在总吞吐里。开了卸载的点在图上多画一圈虚线。

流式间隔的坑

因为指标在客户端测,回复比流式间隔短时会整块到达,TTFT 会把解码时间吞进去。间隔设为 100 token 时,MiniMax M3 约 30% 的请求受影响。规则因此要求每个新增或重跑的点,流式间隔不超过 20 token。

换算公式

  • 每百万 token 成本 = 每芯片小时成本 × 1,000,000 ÷(3600 × 每芯片 tokens/s)。
  • 每美元 token 数是它的倒数形式。看板的默认纵轴就是按自有成本算的"每美元总 token 数"。
  • 每兆瓦吞吐 = 每芯片 tokens/s × 1000 ÷ 全口径功率。这里的功率含主机、网络、制冷,是容量模型,不是实测。实测功率是另一族指标,2026 年 11 月起多节点运行才默认采集。

收入类指标是另一回事

看板还有一族"每 GPU 小时 token 收入"的纵轴,算的是每小时 token 量乘以售价。默认定价是未缓存输入和输出都按每百万 1 美元、缓存输入按 0.10 美元;也可以选 OpenRouter 上的公开价格。计价前会先按缓存命中率给输入打折。看板文档专门提醒:如果把输入价直接乘到原始输入速率上,会把约 92% 的缓存读取按新输入计价,把毛利高估近一个数量级。

150 tokens/s 这条线从哪来

InferenceX 自己不规定统一的服务等级目标,术语表说应在自己的阈值处读曲线。但文章里反复用 150 tokens/s 做比较点。调研只找到一个出处:它是看板利润估算器给 DeepSeek-V4.1-Flash 设的默认目标,选法是"让有报价的官方配置行数最多的最低目标",不是体验研究的结果。其他模型的默认值各不相同,从 Kimi K3 的 60 到 DeepSeek V4 Pro 的 170。

七 · 规则与治理

什么配置能上榜,谁说了算

允许和禁止

事项规则
镜像必须用 vLLM、SGLang 上游仓库的镜像原样运行。不许打补丁、改已安装的包、装分叉版本。唯一例外是随提交附上的豁免文件,写明改了什么和移除计划
启动参数对生产有用的参数必须先写进官方的 vLLM recipes 或 SGLang cookbook,而且上游合并要早于 InferenceX 的合并
优化手段让同一计算跑得更快的都可以;减少模型计算量的不行(例如每隔几层跳过索引器)
引擎顺序每个模型有指定的主引擎(vLLM 或 SGLang),先交主引擎,才能再交 TensorRT-LLM、ATOM 这类厂商引擎
KV 卸载只允许卸载到主机内存,可选。SSD 卸载推迟到后续版本
主机内存上限按所用 GPU 占服务器 GPU 总数的比例分配。没有标准内存配置的机型每台上限 3 TB,理由是防止堆内存的军备竞赛
预填充/解码分离允许
流式间隔不超过 20 token
曲线点数建议每条曲线至少 5 个实测的前沿点

看板上同一个(模型、硬件、引擎)组合只画一条"最佳可用"曲线。曲线上不同的点可以用不同的优化组合,例如有的点开推测解码、有的点开分离式、有的点开卸载。每个点可以点开看配置和 CI 出处。

推测解码:强制接受长度

合成的填充文本上,草稿模型的真实接受率没有意义。AgentX 的做法是让引擎按一个事先定好的接受长度来接受:

  • 每个(模型、思考模式、草稿长度)组合只有一个提交进仓库的标准值。提交方可以选草稿长度,但不能换接受目标。
  • 标准值的测法:在 B300 上用真实推测解码跑 SPEED-Bench 的编程类 80 条提示,读引擎计数器。
  • DeepSeek-V4.1-Flash 的 DSpark,草稿长度 5 时的标准值:思考关 4.07,思考开 3.51。
  • 规则自己承认:合成接受下的结果不能当作任何合规证据;草稿精度降低造成的质量损失会转移到接受率上,而目标模型的质量测试测不到。

"每个数据点都经过精度校验"的实际含义

  • 精度测试是与吞吐分开跑的作业,默认用 GSM8K,下限 0.90(个别模型更高)。DeepSeek-V4.1-Flash 适用默认的 0.90。
  • 不是每个并发点各测一次。每个部署分组在其最高并发点验证一次,同组其余点共享结论。
  • 它确实抓到过正确性故障:有一次握手错误导致 KV 没传过去、解码从头重算,GSM8K 得了 0 分。
  • 批评意见是 GSM8K 太容易,FP4 和 FP8 在上面分数几乎相同,不足以裁定更激进量化的影响。

提交流程

  • 任何人可以提交。流程是:跑出全绿的完整扫描(含精度测试),对应芯片厂商的代码负责人按清单签字,SemiAnalysis 的核心维护者最终批准,然后复用那次运行的结果入库。
  • 不是每晚重跑。早期的 InferenceMAX 是每晚重跑;现在只有提交改动了变更日志时才触发,合并后不再重跑。
  • NVIDIA 和 AMD 各有 5 名具名工程师是各自主配置和配方目录的代码负责人。另有一个 CI 机器人独立复核签字清单,目前只是建议性的。
  • 硬件跑在接入仓库的自托管机器上,算力由厂商和云商赞助:AMD 提供 MI355X 等,NVIDIA 提供 GB200 NVL72 和 B200,另有 Crusoe、CoreWeave、Nebius、TensorWave、Oracle、TogetherAI。
  • 只有官方仓库的结果算"官方"。厂商博客里用 harness 自测的结果按规则须标"非官方"。
  • 没有成文的申诉或仲裁程序。争议实际走 GitHub issue、Slack 和邮件。

八 · 成绩

从 8 月到 11 月:结论一直在动

覆盖范围的变化

  • 首发(8 月 24 日)五个模型:DeepSeek V4 Pro、Kimi K3、MiniMax M3、Qwen3.5、GLM 5.3。硬件从 H200 到 GB300 NVL72,加上 AMD 的 MI300X 到 MI355X。
  • 现在(11 月 10 日)七个活跃模型。首发的三个已被后继版本取代:DeepSeek V4 Pro 和 MiniMax M3 于 10 月 29 日退役,Kimi K3 于 11 月 3 日退役。DeepSeek-V4.1-Flash 于 9 月 10 日加入。
  • Vera Rubin NVL72 在 9 月中出现。TPU 在 9 月进入 InferenceX,但只有固定形状场景的结果,调研时没有找到 TPU 的 AgentX 结果。

首发时的画面

  • MiniMax M3、Qwen3.5、GLM 5.3 上 NVIDIA 明显领先。Qwen3.5 在每用户 90 tokens/s 处领先 20 倍以上;GLM 5.3 在 150 tokens/s 处成本效率最高到 5 倍。
  • DeepSeek V4 Pro 上接近。8 月 21 日之前,MI355X 加 SGLang 与 B200 加 vLLM 的性价比打平;之后 vLLM 的优化让 B200 反超。SemiAnalysis 的说法是"接近的比赛,没有定论"。
  • AMD 的若干胜点只在自家引擎 ATOM 下成立。例如 Kimi K3 上 MI355X 加 ATOM 在端到端延迟 40 到 60 秒那一段胜过 GB300 NVL72 加 vLLM。SemiAnalysis 同时说 ATOM 在生产中几乎没人用;AMD 则要求删掉看板上的相关脚注,称已有商用部署。
  • 机柜级不总是赢。MiniMax M3 上,单节点 B200、B300 按成本归一后胜过 GB200、GB300 机柜。原因是路由器成了瓶颈,宽并行的内核没调好,机柜成本又更高。

十一 · 局限与批评

它没测到什么,谁在质疑

方法上的局限

  • 单一来源。一家公司的员工、一个客户端、只有编程。SemiAnalysis 承认请求分布随客户端和分词器而变,辩护理由是相当大一部分智能体编程流量走 Claude Code。
  • 合成内容。凡依赖 token 内容的技术,在填充文本上的表现都不能代表真实表现。官方只针对推测解码做了补救(强制接受长度),而补救用的是平均值。有论文指出合成输入会高估推测解码的真实吞吐。
  • 闭环。会话内部闭环是智能体的本来面目,但真实服务里"新会话的到达"是开环的。定并发加会话回收测不出过载、排队崩溃和准入控制。官方自己承认,不同配置在同一小时内完成的请求数不同,遇到的负载组合有差异,低并发时最明显。
  • 一小时窗口。超过一小时的会话尾部、主机内存卸载层填满后的稳态都观察不全。
  • 5 分钟空闲上限。其他研究指出缓存未命中恰恰集中在人为停顿之后,把长间隔截短会改变这类未命中的形态。
  • 不测任务成功。官方多处明说。这也使跨模型的成本对比容易被误读:vLLM 博客曾用 AgentX 数字算出相对某闭源 API 价格 14 到 106 倍的成本优势,并注明比的是服务成本而非模型质量。

利益关系

  • 硬件由被测厂商提供,发布文章里并列引用了被测方高管的背书。
  • 成本和功耗换算用的是 SemiAnalysis 自己出售的模型。
  • 负载生成器出自 NVIDIA。
  • 没有找到 SemiAnalysis 针对利益冲突的专门声明。通用说法是"独立、厂商中立、可复现",并举出 AMD 在若干配置上胜出的结果。

找到的外部批评

数量很少,而且都带立场:

  • 一位 Hacker News 用户称这类基准是厂商高度调过的,措辞激烈,没有随附证据。
  • 一位看多 NVIDIA 的分析者批评 9 月的 TPU 文章把 NVIDIA 一侧四项优化关掉后称为同等条件比较。针对的不是 AgentX 本身。
  • GitHub 上有用户质疑功能不对等(比的其实是引擎和编译器),以及分离式配置的每 GPU 归一口径。
  • 一位复现者发现自己的解码比官方数字快很多,而闭环会把这种差异放大到 TTFT 上。另有记录显示同一配方在两台同型号节点上相差 12%。

没有找到独立的方法论评审,也没有找到对 AgentX 数字的系统性复现。"被广泛复现和验证"是 SemiAnalysis 的说法。调研时搜索额度中途用尽,The Register 的报道和社交媒体上的讨论没有查全,不能断言不存在。

十二 · 回到 vLLM 博客

用这些知识重读两篇博客的数字

博客里的说法现在可以怎么读
每 GPU 954K tokens/s总计口径,缓存命中的输入每轮重复计入。按数据集约 200:1 的输入输出比粗估,其中真正生成的输出只占百分之零点几,也就是每 GPU 几千 tokens/s 的量级。博客的交互图上有"仅输出"切换,精确值以它为准
P90 每用户 196 tokens/s90% 的请求,其平均 token 间隔不超过约 5.1 毫秒。每请求一个样本
7.9 倍于单节点结果两条曲线在同一交互速度处的吞吐之比。比值随所取的交互速度而变
每 GPU 小时 38.96 美元把吞吐按 DeepSeek 非高峰 API 价格折算的假想收入,不是成本也不是利润。博客没有给出各类 token 的单价、假设的命中率和公式;看板代码里也没有对应的 DeepSeek 价格选项。作为参照,看板给 GB300 的自有成本是每 GPU 小时 2.31 美元
第一篇的"150 TPS 约束下 5.3 倍"150 是看板给这个模型设的默认目标,没有体验依据
用的哪版数据集按仓库规则,DeepSeek-V4.1-Flash 用完整版(上下文最长约 1M)
推测解码的收益按强制接受长度计入。DSpark 草稿长度 5 时,思考关按 4.07、思考开按 3.51
SWA 有界重放的精度AgentX 的旁路门槛是 GSM8K 不低于 0.90。长程智能体任务上的质量影响,AgentX 测不到
成绩是不是官方的博客图注链接到看板上的官方曲线。但文中自建的测量(单步前向时间、镜像与滞后重放等)是 vLLM 自己的诊断,不是 AgentX 结果

还有一层背景值得知道:vLLM 的主要开发方是 Inferact,而 vLLM 在 AgentX 规则里是被指定的两个主引擎之一。看板每个模型的主引擎名额在 vLLM 和 SGLang 之间对半分。11 月的看板上,DeepSeek-V4.1-Flash 在 B300 和 GB300 上的最佳开源引擎点是 SGLang,不是 vLLM。

十三 · 清单

有人引用 AgentX 数字时,先问这十二个问题

  1. 哪条纵轴?仅输出,还是含缓存的总 token?每 GPU、每美元,还是每兆瓦?
  2. 哪条横轴、什么阈值?常规交互速度、整响应口径,还是端到端归一化?阈值是不是恰好取在对手曲线的端点?
  3. 是实测点还是插值?
  4. TTFT 是多少?官方自己说交互速度和 TTFT 必须一起看。
  5. 哪个数据集变体?完整版还是 256k 版?两者的输入中位数差近一倍。
  6. 哪个引擎?上游的 vLLM、SGLang,还是厂商自己的运行时?
  7. 拿谁当基线?对手用的是它最强的引擎吗?
  8. 开了什么?推测解码、分离式、KV 卸载、哪种并行?一条曲线上的不同点可能是不同的组合。
  9. 哪一天的运行?数字隔天就可能变两位数百分比,模型也在快速轮换。
  10. 是官方结果吗?有没有 CI 运行链接?
  11. 成本用的谁的价格?自有、租赁,还是引用者自己的假设?是成本还是折算收入?
  12. 这个负载像你的负载吗?Claude Code、编程、输入中位数 14 万 token、输出 444 token、5 分钟缓存有效期。聊天、检索增强、长输出类负载的排名可能完全不同。
可靠程度

这份报告本身有多可靠

  • 把握最高的部分:数据集、重放机制、指标公式、成本常量、规则与流程。它们直接取自 2026-11-10 当天的仓库代码、文档和数据集文件。代码会变,引用时请带日期。
  • 把握中等的部分:成绩与厂商反应。抓取工具的额度中途用完,部分文章只读到摘要或搜索片段;看板数字只读了一个阈值档位。
  • 把握较低的部分:外部批评和同类对比。搜索没有做完;MLPerf 的信息是二手的。
  • 没有查到的:贡献者的征集与同意流程;子集的抽样方法;跑一次的成本;38.96 美元的算法;TPU 的 AgentX 结果;1.1 版本的内容和日期;SemiAnalysis 与被测厂商之间是否有付费关系的公开披露。
  • 分布统计是自算的。第二节的分位数由调研时下载公开数据集后统计得出,其中两个中位数和会话占比与官方数字吻合,其余没有官方值可对照。
