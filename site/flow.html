AgentX 数据集中的一条会话:它是怎么被测的

先不管并发。只放 AgentX 数据集中的一条会话(编号 00ca01c4aaec…,29 轮主对话加 6 次子智能体请求),看压测程序拿到什么、设了什么、发出什么、收回什么,以及每一轮过后哪些东西变了。

35 次请求合计输入 3,971,584 · 输出 35,287这条会话的输入是怎么攒出来的 →AgentX 的重放机制 →

一、三个角色

剧本

数据集里的一条会话
  • 35 行,一行是一次请求
  • 输入多少 token、由哪些块组成
  • 输出多少 token
  • 离上一次请求结束隔了多久
  • 属于主智能体还是哪个子智能体
  • 没有任何文字
→

压测程序

agentx-harness,扮演 Claude Code
  • 把块编号变回一段段文字
  • 照剧本一行一行发请求
  • 等够间隔再发下一行
  • 掐表、记数
  • 不看模型写了什么
⇄

被测系统

引擎 + DeepSeek-V4.1-Flash + 硬件
  • 真的把输入读一遍
  • 真的一个个 token 写出来
  • 自己决定缓存留什么、留多久
  • 不知道自己在被测
成绩单:每次请求留下一行,四个数:首 token 时间、总耗时、输入 token 数、输出 token 数。这条会话跑完一共 35 行。模型写出来的文字不进成绩单。

二、开跑之前就定死的东西

下面这些在整条会话里不变。上半部分由 AgentX 的规则锁定,参赛者改不了;下半部分由参赛者自己定,但跑起来之后也不能动。

配置项取值为什么这样定
压测程序这边(规则锁定)
接口OpenAI 兼容的 /v1/chat/completions,强制流式首 token 时间和 token 间隔要在客户端量,必须流式
模型名剧本里记的原模型名,一律改成被测模型主智能体和子智能体的请求都打到同一个模型上
分词器被测模型自己的分词器保证"一块 64 token"在被测模型眼里也是 64 个左右
随机种子42同一个块编号永远变成同一段填充文字,每次跑都一样
max_tokens每轮不同,等于剧本里这一轮的输出 token 数输出长度由剧本定,不由模型定
ignore_eostrue,不许改模型想提前收尾也不行,必须写满
历史里的模型回答填充文字,长度等于剧本里记的输出不用被测模型刚写的内容,所以下一轮的输入人人相同
工具结果默认当作普通的 user 消息发剧本里没有工具的格式信息
播放标记在第一条 user 消息前插一个 [rid:12 位十六进制],这次播放从头到尾用同一个防止同一条会话的另一次播放蹭到这次的缓存
等待照剧本的间隔等;整棵会话树闲置超过 300 秒,按 300 秒算保留真实的节奏,又不让长停顿把时间耗光
token 计数以服务器返回的 usage 为准发出去的文字会被服务器重新分词,数量可能差几个
被测系统这边(参赛者自己定)
引擎和版本vLLM、SGLang 等,用上游镜像原样运行不许给引擎打补丁
并行方式几张卡、怎么切分模型、预填充和解码是否分开这是参赛者真正在调的东西
缓存前缀缓存留多大,是否卸载到主机内存决定图上绿色部分能不能真的省下来
推测解码可以开;接受长度强制设为公布的固定值填充文字上的真实接受率没有意义
流式间隔不超过 20 token 回传一次攒太多再发,客户端量不准首 token 时间

三、一次请求的往返

拿第 3 轮做例子。时间从上往下走,左边是压测程序做的事,右边是被测系统做的事,中间的箭头是网络上传的东西。

压测程序在一次请求里只关心时间怎么切:

等待(不计入)
排队 + 读输入 → 首 token 时间
解码 767 个 token → 总耗时 − 首 token 时间

这一次请求的"token 间隔" = (总耗时 − 首 token 时间) ÷ (输出 token 数 − 1)。每次请求算出一个值,就是一个样本。

第 ④ 步发出去的请求大致长这样(填充文字用省略号代替,rid 的值是示意):

POST /v1/chat/completions
{
  "model": "deepseek-ai/DeepSeek-V4.1-Flash",
  "stream": true,
  "max_tokens": 767,          ← 剧本里这一轮的输出数
  "ignore_eos": true,
  "messages": [
    {"role": "system",    "content": "……"},                      ← 填充文字
    {"role": "user",      "content": "[rid:3f9a1c0b7e52]\n\n……"},  ← 开头带播放标记
    {"role": "assistant", "content": "……"},                      ← 填充文字,约 250 token(上一轮的录制输出长度)
    {"role": "user",      "content": "……"}                       ← 这一轮新来的内容
  ]
}

前两条消息合起来是 64,128 token,具体怎么分给 system 和 user,这条会话的数据里看不出来。

四、整条会话的时间线

把 35 次请求按时间排开。每个色块是一次请求从发出到收完,色块之间的空白是等待。子智能体在第 5 轮之后被派出去,三个同时跑,主智能体等它们都结束才发第 6 轮。

主智能体的请求子智能体的请求超过 300 秒的停顿,重放时压到 300 秒

这张图画的是录制时的时间线。重放时有两处不同:色块的宽度换成被测系统自己的耗时,这正是要测的东西;3 段超过 300 秒的停顿被压短,合计少等 323 秒。其余空白照原样等。把鼠标停在色块上可以看是哪一轮。

"缓存里已有"是理想情况:假定被测系统把这条会话之前的前缀一直留着。留不住的话,那一轮的"需要新算"就等于整条输入。第 1 轮是一次很小的请求,和后面的轮次不共用内容。第 18 轮的输入比第 17 轮略短,所以没有新增。

每一轮都在变的

  • 输入:比上一轮多一截,从 64,128 长到 169,024
  • max_tokens:换成这一轮的录制输出数
  • 发之前等多久:换成这一轮的录制间隔
  • 服务器的缓存:这条会话的前缀又长了一截
  • 成绩单:多一行

从头到尾不变的

  • 第二节里的全部配置
  • 块编号到填充文字的对应关系
  • 播放标记 rid
  • 剧本本身:无论模型写了什么,下一行照发
  • 模型权重和被测系统的部署

六、这条会话跑完,留下什么

  • 35 个延迟样本。每次请求一个首 token 时间、一个 token 间隔。评测最后对所有样本取 P90,token 间隔的 P90 取倒数就是"交互速度"。
  • 4,006,871 个计入吞吐的 token。其中输入 3,971,584、输出 35,287。默认口径把缓存命中的输入也算进去。
  • 真正要算的只有一小部分。缓存一直留得住的话,需要新读的输入是 293,440 token,加上输出共 328,727,占全部的 8%。
  • 没有留下的:模型写的文字、答得对不对。答题质量由另一套单独的精度测试把关。

七、从四个数到全部指标

成绩单上每次请求只有四个原始数。所有指标都由它们算出,成本和能耗类再配上几个查表得来的常数。

符号含义来源
每次请求量到的四个数(第 i 次成功请求)
TTFTi首 token 时间(秒):发出请求到第一个 token 返回客户端掐表
Li总耗时(秒):发出请求到最后一个 token 返回客户端掐表
ISLi输入 token 数,完整输入,不区分是否命中缓存服务器返回的 usage
OSLi输出 token 数,思考 token 也算在内服务器返回的 usage
不来自请求的量
T时间窗(秒)= 最晚的请求结束时刻 − 最早的请求开始时刻,约 3,600由请求的起止时刻算出
G芯片数。预填充和解码分开部署时,算整个部署的全部芯片部署配置
h理论缓存命中率 = 命中的块数 ÷ 总块数,假定缓存无限大由剧本算出,与被测系统无关
C每芯片小时成本(美元)。例:GB300 NVL72 自有 2.31、租用 5.00SemiAnalysis 的常数表
P每芯片的全包供电功率(千瓦),含主机、网络、制冷。例:GB300 NVL72 为 2.12SemiAnalysis 的常数表

统计范围是测量窗口内的全部成功请求。预热请求和出错的请求不算。

延迟类:每次请求一个样本,再取分位数

指标公式说明
首 token 时间P90( TTFTi )包含排队和读输入的时间
token 间隔 ITLITLi = ( Li − TTFTi ) ÷ ( OSLi − 1 )
再取 P90( ITLi )		也叫 TPOT。是一次请求内的平均间隔,不是逐个 token 的间隔
交互速度1 ÷ P90( ITLi )单位 tok/s/user,曲线的横轴。先取 P90 再取倒数,所以是慢的那一头
端到端延迟P90( Li )主要被最长的那批输出拖着走,在 AgentX 里参考价值小
端到端归一化交互速度1 ÷ P90( Li ÷ OSLi )实验性指标。把首 token 的等待也摊进去,输出越短惩罚越重

吞吐类:全部请求求和,再除以时间和芯片数

指标公式说明
输入吞吐Σ ISLi ÷ T ÷ G单位 tok/s/chip。被复用的前缀每一轮都重新计一次
输出吞吐Σ OSLi ÷ T ÷ G
总吞吐( Σ ISLi + Σ OSLi ) ÷ T ÷ G默认口径,曲线的纵轴由它派生
未缓存口径的输入吞吐输入吞吐 × ( 1 − h )只算每轮新增的输入
未缓存口径的总吞吐输入吞吐 × ( 1 − h ) + 输出吞吐看板上叫 Horace He metric,目前不是默认显示
每秒完成请求数按 1 秒窗口数完成的请求,再取均值或分位数

成本和能耗类:吞吐乘以常数

下表的"吞吐"可以代入总、输入、输出三种,各得一套数字。

指标公式说明
每百万 token 成本C × 1,000,000 ÷ ( 3600 × 吞吐 )单位美元
每美元 token 数吞吐 × 3600 ÷ C看板默认的纵轴,用自有成本
每兆瓦吞吐吞吐 × 1000 ÷ P单位 tok/s/MW。P 是容量模型里的数,不是实测功率
每 token 焦耳实测平均功率(瓦) ÷ 每秒 token 数分"每输出 token"和"每总 token"两种

收入类:再加上售价

指标公式说明
计费输入吞吐输入吞吐 × ( 1 − 命中率 × ( 1 − 缓存读取价比例 ) )这里的命中率用服务器实测值。缓存读取价比例默认 10%
每芯片小时收入3600 × ( 计费输入吞吐 × 输入价 + 输出吞吐 × 输出价 )默认定价:未缓存输入和输出各 $1 / 百万 token

代入这条会话

只有能从剧本直接得出的部分算得出来:

  • Σ ISL = 3,971,584,Σ OSL = 35,287,合计 4,006,871 个 token 计入总吞吐。
  • 理论缓存命中率 h = 93%。未缓存口径下计入的是 328,727 个 token,约为总口径的 8%。
  • 延迟类的指标一个也算不出来,因为 TTFT 和 L 要实测才有。吞吐类也缺 T 和 G。

公式按 AgentX 聚合脚本和看板文档的口径整理。其中"每 token 焦耳"和"每芯片小时收入"两条是按定义写出的,资料里只有字段名和文字描述,没有逐字的公式。token 间隔另有一种算法,区间算到 HTTP 响应结束而不是最后一个内容块,看板对 AgentX 优先用那一种,数值略大。

八、AgentX 做了哪些简化和假设

前面七节讲的流程,每一步都对真实情况做了取舍。这些取舍大部分是 SemiAnalysis 自己写在文档里的,少数是官方没有明说、但从规则能推出来的。两类分开列。

官方文档里写明的

简化或假设官方怎么说出处
只有一种来源393 条全部是 Claude Code 的会话。承认请求分布随智能体框架而变,也随模型的分词器而变。理由是全球很大一部分智能体编程流量走 Claude Code。说下一版会覆盖更多模型和框架发布长文
内容是合成的填充文字承认推测解码的接受、拒绝数会异常,因为草稿模型没在这种数据上训练过。补救办法是强制一个固定的接受长度发布长文、仓库规则
合成内容下的接受率不算证据仓库规则明说,合成 AgentX 下的接受率不能作为任何合规证据仓库规则
闭环重放承认不同配置在同一小时内完成的请求数不同,遇到的负载组合有自然差异,低并发时最明显。理由是智能体的后一步依赖前一步的结果,不可能预先发出。文章自己链接了一篇批评闭环基准的博客发布长文、方法页、方法博客
低并发样本少承认低并发时收敛差发布长文
停顿压到 300 秒说明是为了能在一小时内跑完。300 秒对应 Anthropic 默认的缓存有效期发布长文
时间戳不等于因果承认 HTTP 时间戳看不出主智能体是在等子智能体,还是在做别的事。称这是"小局限",希望后续版本改进发布长文
看不到供应商一侧的内容承认聊天模板、专有分词器、服务端工具、加密的思考内容、图片和文档展开成多少 token,都只能用占位和按模型校准的填充来近似发布长文、方法页
公开的只是子集说明 393 条是从 8,271 条里选出的"有代表性的子集"发布长文、方法页
指标不完美说端到端延迟在 AgentX 里意义变小;交互速度和首 token 时间必须一起看;端到端归一化交互速度"有意不完美";人们真正在乎的是任务端到端完成的速度,新指标还在定义发布长文、术语表
内存卸载上限是人为规则承认本地生成器对所有机型都套了 3 TB 上限,例外情形还没实现发布长文

官方没有明说,从规则推出来的

  • 行为没有校准。官方只校准了 token 数(比值中位数 1.004)。输出多长、用多少轮、什么时候派子智能体,都是 Claude 的行为。被测模型真去干同样的活,会走出不同的轨迹。
  • 依赖内容的技术都测不准。官方只提了推测解码。按同样的道理,内容感知的缓存淘汰、提示压缩、基于注意力稀疏性的方法,在填充文字上的表现也不代表真实表现。
  • 模型自己何时停不在测量范围内。输出长度被 ignore_eos 钉在录制值上。
  • 筛选有偏。入选规则要求至少 20 个请求、并发子智能体不超过 10 个,短会话和极端扇出的会话被排除。抽样方法和与母语料的分布对照没有公布。
  • 测不出过载。会话数固定,跑完一条换一条,没有"新用户不断到来"的过程,所以排队崩溃和准入控制的行为观察不到。
  • 一小时看不全长期状态。跨小时的缓存淘汰、内存卸载层填满后的稳态,都在窗口之外。

对应到这条会话

  • 图上的 35 次请求,输出长度和间隔都是原模型留下的。DeepSeek 真做这个任务,轮数和每轮的长度都会不同。
  • 3 段超过 300 秒的停顿被压短。真实使用里,这几段停顿正是缓存最可能被挤掉的时候。
  • 主智能体和子智能体原本用不同的模型,重放时都打到同一个被测模型上。

出处:发布长文是 SemiAnalysis 的 AgentX - InferenceXv3(含 Future Next Steps 一节);方法页是 AgentX Methodology;方法博客是 Agentic Benchmark for LLM Inference: Metrics and Methodology。本节按调研笔记整理,没有重新打开原文逐条核对;发布长文的前半部分没有通读,相关表述可能有遗漏。更完整的版本和各方批评见 AgentX 调研的局限一节。

九、还没讲的

正式评测在这之上再叠三件事:每条会话从中间某处切入并先预热缓存;很多条会话同时跑;只统计一小时窗口里的请求。这些见 AgentX 调研的重放一节。

本页的流程按 AgentX 压测程序的方法文档整理,没有在真机上跑过;图里没有任何实测耗时。请求示例里的字段是按文档拼的示意,不是抓包。
